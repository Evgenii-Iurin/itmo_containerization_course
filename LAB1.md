# Анализ Dockerfile: Плохие и Хорошие Практики

## Обзор

Этот документ описывает плохие практики в `Dockerfile.bad`, их исправления в `Dockerfile`, а также общие рекомендации по использованию контейнеров.

---

## Плохие Практики в Dockerfile.bad

### 1. Использование `python:latest` вместо конкретной версии

**Проблема:**
```dockerfile
FROM python:latest
```

**Почему это плохо:**
- Непредсказуемое поведение: образ может измениться между сборками
- Невозможность воспроизвести сборку в будущем
- Риск несовместимости с зависимостями проекта
- Нарушение принципа детерминированности сборок

**Исправление в хорошем Dockerfile:**
```dockerfile
FROM python:3.11-slim
```
- Используется конкретная версия Python (3.11)
- `slim` вариант уменьшает размер образа
- Гарантирует стабильность и воспроизводимость

---

### 2. Установка ненужных пакетов для production

**Проблема:**
```dockerfile
RUN apt-get update && apt-get install -y \
    vim \
    curl \
    wget \
    git \
    build-essential \
    && rm -rf /var/lib/apt/lists/*
```

**Почему это плохо:**
- Увеличивает размер образа (на десятки мегабайт)
- Расширяет поверхность атаки (больше уязвимостей)
- Увеличивает время сборки
- Замедляет запуск контейнера
- Для production не нужны инструменты разработки (vim, git)

**Исправление в хорошем Dockerfile:**
```dockerfile
# slim образ уже минималистичен, дополнительных пакетов не требуется
```
- Используется `python:3.11-slim` - минимальный образ
- Устанавливаются только необходимые зависимости через poetry
- Размер образа значительно меньше

---

### 3. Копирование всех файлов сразу (плохое кэширование слоёв)

**Проблема:**
```dockerfile
COPY . /app
```

**Почему это плохо:**
- При любом изменении в проекте Docker пересобирает все последующие слои
- Зависимости переустанавливаются даже при изменении только кода
- Увеличивается время сборки
- Неэффективное использование кэша Docker

**Исправление в хорошем Dockerfile:**
```dockerfile
# Сначала копируем файлы зависимостей
COPY pyproject.toml poetry.lock* README.md ./
RUN poetry install ...

# Затем копируем исходный код
COPY src/services/router/ ./src/services/router/
```
- Файлы зависимостей копируются отдельно
- Зависимости устанавливаются до копирования кода
- При изменении только кода, слой с зависимостями переиспользуется из кэша

---

### 4. Установка зависимостей без предотвращения кэширования pip

**Проблема:**
```dockerfile
RUN pip install poetry==2.2.1 && \
    pip install --upgrade pip && \
    poetry config virtualenvs.create false && \
    poetry install --no-interaction --no-ansi --extras langchain
```

**Почему это плохо:**
- Кэш pip создаётся и остаётся в образе, увеличивая его размер
- Не используется флаг `--no-cache-dir` для pip
- Кэш занимает место в образе без необходимости

**Исправление в хорошем Dockerfile:**
```dockerfile
ENV PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

RUN pip install --no-cache-dir poetry==2.2.1 && \
    poetry config virtualenvs.create false && \
    poetry install --no-interaction --no-ansi --no-root --extras langchain
```
- Установлена переменная окружения `PIP_NO_CACHE_DIR=1` для глобального отключения кэша
- Используется `--no-cache-dir` для явного предотвращения кэширования
- Кэш не создаётся, поэтому не требуется его очистка
- Уменьшение размера образа за счёт отсутствия кэша

---

### 5. Запуск от root пользователя

**Проблема:**
```dockerfile
# Нет USER директивы - контейнер работает от root
```

**Почему это плохо:**
- Серьёзная уязвимость безопасности
- При компрометации контейнера злоумышленник получает root доступ
- Нарушение принципа минимальных привилегий
- Проблемы с правами доступа к volume

**Исправление в хорошем Dockerfile:**
```dockerfile
RUN groupadd -r appuser && useradd -r -g appuser appuser && \
    chown -R appuser:appuser /app

USER appuser
```
- Создаётся непривилегированный пользователь `appuser`
- Права на директорию передаются этому пользователю
- Контейнер запускается от непривилегированного пользователя
- Снижение рисков безопасности

---

### 6. Отсутствие переменных окружения для production

**Проблема:**
```dockerfile
# ENV не установлены
```

**Почему это плохо:**
- Нет оптимизации Python (буферизация, байт-код)
- Нет контроля над поведением pip
- Сложнее управлять конфигурацией

**Исправление в хорошем Dockerfile:**
```dockerfile
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1
```
- `PYTHONUNBUFFERED=1` - вывод без буферизации (важно для логов)
- `PYTHONDONTWRITEBYTECODE=1` - не создавать .pyc файлы
- Оптимизация работы pip

---

### 7. Хардкод порта в CMD

**Проблема:**
```dockerfile
CMD ["uvicorn", "src.services.router.app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Почему это плохо:**
- Невозможно изменить порт без пересборки образа
- Нарушение принципа конфигурируемости
- Сложнее использовать в разных окружениях

**Исправление в хорошем Dockerfile:**
```dockerfile
ENV PORT=8000
CMD ["sh", "-c", "uvicorn src.services.router.app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]
```
- Порт задаётся через переменную окружения
- Можно переопределить при запуске: `docker run -e PORT=9000 ...`
- Значение по умолчанию через `${PORT:-8000}`

## Плохие Практики Использования Контейнеров

### 1. Монтирование volume с данными без резервного копирования

**Проблема:**
```bash
docker run -v /host/data:/container/data myapp
```

**Почему это плохо:**
- Данные на хосте могут быть потеряны при удалении контейнера
- Нет автоматического резервного копирования
- Риск потери данных при сбое хоста
- Сложно мигрировать данные между хостами

**Решение:**
- Использовать именованные volumes: `docker volume create mydata`
- Настроить регулярное резервное копирование
- Использовать volume драйверы с поддержкой бэкапов
- Документировать процесс восстановления данных

---

### 2. Запуск контейнеров с привилегированным доступом без необходимости

**Проблема:**
```bash
docker run --privileged myapp
# или
docker run --cap-add=ALL myapp
```

**Почему это плохо:**
- Контейнер получает почти полный доступ к хосту
- При компрометации контейнера злоумышленник может получить доступ к хосту
- Нарушение изоляции - основного преимущества контейнеров
- Риск эскалации привилегий

**Решение:**
- Использовать минимально необходимые capabilities: `--cap-add=NET_ADMIN`
- Запускать от непривилегированного пользователя (см. исправление практики #5)
- Использовать `--read-only` для файловой системы где возможно
- Применять AppArmor/SELinux профили для дополнительной защиты

---

## Когда НЕ стоит использовать контейнеры

### 1. Приложения с жёсткими требованиями к производительности и низкой задержке

**Почему:**
- Контейнеры добавляют слой абстракции и небольшие накладные расходы
- Для приложений реального времени (HFT, игры, стриминг) каждая микросекунда важна
- Прямой доступ к железу может быть критичен
- Виртуализация может вносить непредсказуемые задержки

**Альтернативы:**
- Нативные приложения на хосте
- Bare metal deployment
- Специализированные решения (DPDK для сетевых приложений)

**Примеры:**
- Высокочастотная торговля (HFT)
- Системы управления промышленным оборудованием
- Приложения для обработки аудио/видео в реальном времени с жёсткими требованиями

---

### 2. Простые статические сайты или простые скрипты без зависимостей

**Почему:**
- Избыточность: контейнеризация добавляет сложность без выгоды
- Простые статические сайты лучше обслуживать через CDN (Cloudflare, AWS CloudFront)
- Простые скрипты можно запускать напрямую на хосте
- Дополнительные накладные расходы на управление контейнерами

**Альтернативы:**
- Статические сайты: CDN, GitHub Pages, Netlify
- Простые скрипты: cron jobs, systemd timers
- Простые CLI утилиты: прямой запуск

**Примеры:**
- Простой HTML/CSS/JS сайт-визитка
- Одноразовый Python скрипт для обработки данных
- Простые bash скрипты для автоматизации

**Исключения:**
- Если нужна изоляция окружения
- Если скрипт требует специфических зависимостей
- Если нужна консистентность между окружениями

## Монтирование Volume (Обязательное требование)

В хорошем Dockerfile volume должен быть правильно настроен. Пример использования:

```bash
# Создание volume для данных приложения
docker volume create app_data

# Запуск контейнера с volume
docker run -v app_data:/app/data myapp

# Или с bind mount для разработки
docker run -v $(pwd)/data:/app/data myapp
```

В `docker-compose.yml` volume должен быть определён:

```yaml
services:
  app:
    volumes:
      - app_data:/app/data
      - ./logs:/app/logs  # для логов

volumes:
  app_data:
```

**Важно:**
- Использовать именованные volumes для production данных
- Настроить правильные права доступа (см. практику #5 про пользователя)
- Документировать какие данные хранятся в volume
- Настроить резервное копирование volume

## Заключение

Следование хорошим практикам при создании Dockerfile и использовании контейнеров:
- Улучшает безопасность
- Уменьшает размер образов
- Ускоряет сборку и развёртывание
- Повышает надёжность и воспроизводимость
- Упрощает поддержку и отладку

Всегда оценивайте необходимость контейнеризации для конкретного случая использования.
